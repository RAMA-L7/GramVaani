## Role assignment (provisional) and constraints

| Role | Provisional holder | May user provisionally hold? | External/qualified guidance or independence required |
|---|---|---|---|
| Research Lead | **User** | **Yes (provisional).** User may coordinate planning, document decisions, and hold operational accountability if capacity/competence allows. | **Qualified external guidance required** for legal/DPDP applicability, ethics/IEC questions, and any determinations outside user's competence; do not self-certify legal/ethics approval. |
| Safeguarding Lead | **[UNRESOLVED — user may provisionally hold coordination role only if explicitly accepted and competent]** | **Possible as provisional coordinator**, but only with explicit written acceptance of responsibilities and limits. | **Must obtain qualified external guidance/confirmation** for local/district child-protection escalation pathways and safeguarding practice; local/institutional authorities must confirm applicable pathway/contacts (not invented). Safeguarding decisions requiring specialist judgment must be escalated. |
| Data/Security Owner | **[UNRESOLVED — user may provisionally hold]** | **Yes (provisional)** for documenting/selecting controls the user can competently implement (device encryption, restricted storage, access separation). | **Qualified external guidance required** where security, hosting/third-party processing, backup/retention enforceability, or legal/notification obligations are uncertain. |
| Consent Reviewer (fluent Telugu reviewer) | **[UNRESOLVED — must be a fluent Telugu reviewer; not the drafter acting as sole approver]** | **No, not as the sole/independent reviewer if user is not demonstrably fluent and independent for this purpose.** User may coordinate but must obtain a fluent Telugu human review. | **Required:** fluent Telugu human reviewer (language/cultural appropriateness, accuracy vs intended meaning). Review must be recorded with reviewer identity/role, date, version, and outcome/changes. |
| Technical Tester | **[UNRESOLVED — user may provisionally hold]** | **Yes (provisional)** if user has access to target device/browser and follows checklist. | No external qualification required by default, but evidence must be actual test records; do not claim voice/ASR accuracy (D-12). Live mic acceptance is **not** a prerequisite for observation-only research. |

**Rule:** The same person may provisionally hold multiple roles, but each role, responsibility, and limit must be explicit and evidenced where required. Role-holding does not substitute for required approvals, reviews, or qualified external guidance.

## Public-safe vs private operational evidence

| Category | Public-safe (may live in public repo, if non-identifying and non-sensitive) | Private/off-repo (must stay in private storage) |
|---|---|---|
| Governance status | Blocker/status registers, protocol versions, template checklists, anonymized decision-log entries that contain no personal contact details, approval IDs tied to individuals, or confidential advice. | Signed approvals, counsel/IEC correspondence, reviewer identity/contact details where private, named sign-off records, dated approval letters/emails, institutional determinations. |
| Consent materials/process | Draft/approved script text, version history, review-status statements, blank consent templates, anonymized administration procedure. | Completed/signed consent records, participant questions containing personal context, any records linking participant identity/code/contact to consent. |
| Safeguarding/incident | High-level procedure/framework, role descriptions without personal contact details, anonymized/de-identified incident-summary templates. | Named safeguarding/incident contacts, local child-protection pathway contacts/instructions as provided by authorities if sensitive, incident reports, disclosures, escalation communications, notification records. |
| Data/storage/security | Data-category framework, retention/deletion policy structure, generic control descriptions (e.g. "encrypted restricted storage") without secrets/locations that increase risk. | Storage locations/paths/accounts, access-control lists, credentials/secrets, backup configurations, device identifiers, audit logs with sensitive metadata, deletion execution logs tied to participants/codes, linkage files. |
| Recruitment/participants | Neutral recruitment script templates, eligibility criteria, anonymized outreach-status summaries. | Participant names/contacts, scheduling communications, intermediary communications containing identities, signed participation records, any linkage keys. |
| Technical testing | Test checklist template, anonymized/pass-fail summaries without sensitive device/account identifiers. | Raw recordings/test audio, screenshots/logs containing personal data, device identifiers or account/session details that should not be public. |

Use `research/instruments/PRIVATE_EVIDENCE_CHECKLIST.md` (template) to track private artifacts and linkage; store actual evidence only in approved private/off-repo storage.
